# Pitfalls Research

**Domain:** Personal macOS dotfiles with symlink-based management
**Researched:** 2026-03-30
**Confidence:** HIGH

---

## Critical Pitfalls

### Pitfall 1: Hardcoded Username and Absolute Paths Baked Into Tracked Files

**What goes wrong:**
Configurations that are symlinked into `~/.claude` or `~/.config` embed `/Users/aslaii` as a literal path. When this repo is cloned by the same user on a new machine it usually works — but if the username ever changes, or a second user bootstraps from the same repo, every embedded path silently breaks at runtime rather than at setup time. This already exists in `claude/settings.json` (hook commands use `/Users/aslaii/.claude/hooks/...`) and in the MCP server definition in `initial-setup-macos.sh` (`/Users/aslaii`).

**Why it happens:**
Tools generate config files that use the active user's home directory as a literal string. Developers accept the generated output without replacing it with a portable form (`$HOME`, `~`, or `$(brew --prefix)`). The breakage is invisible until the repo is used on a different account.

**How to avoid:**
Replace all `/Users/aslaii` literals in tracked files with `$HOME` or `~` where the consuming tool supports it. Where a tool requires a resolved absolute path at write-time (e.g., JSON config files that don't expand env vars), generate the file from a template in the setup script using `sed` or `envsubst` so the path is computed dynamically on each bootstrap run. The `ensure_expected_user` guard in `initial-setup-macos.sh` is a safety net, not a solution — it enforces single-user use rather than fixing portability.

**Warning signs:**
- `grep -r '/Users/' $(git ls-files)` returns any results
- A new machine setup fails with "file not found" on hook commands
- Claude Code hooks silently do nothing (hook path is wrong but Claude Code swallows the error)

**Phase to address:**
Path portability / AI config hardening phase.

### Pitfall 2: Secrets Leaking Through AI Assistant Config Files

**What goes wrong:**
MCP server definitions, AI assistant settings files, and memory files can contain API keys, OAuth tokens, or database URIs in plaintext. These files are candidates for version control because the non-secret portions (model preferences, tool lists, instruction context) belong in the repo. Once a secret lands in git history it is exposed permanently — `git filter-repo` is the only recovery, and it rewrites history.

**Why it happens:**
AI tools like Claude Code and Gemini CLI store all configuration in a single JSON or TOML file. Developers want to version the settings but the file also holds authentication state generated by the tool. The boundary between "safe to commit" and "must not commit" is not enforced by the tool.

**How to avoid:**
Maintain a strict two-layer pattern: track only the skeletal config (tool options, model selection, MCP server URLs without credentials), and keep auth state in gitignored files. The existing `claude/.gitignore` does this correctly — it explicitly names `state.json`, `mcp-oauth-tokens*.json`, and `installation_id` as ignored. The `gemini/` subdirectory lacks its own `.gitignore` and relies on the root `.gitignore` alone — any future tool added in its own subdirectory needs the same protection. Add a pre-commit hook that scans staged files for credential patterns (regex for `[A-Za-z0-9_-]{20,}` in JSON string values, known secret prefixes like `sk-`, `gh_`, `AIza`).

**Warning signs:**
- A new tool's config directory has no `.gitignore`
- `git diff --staged` for a settings file shows new string values that look like tokens
- `trufflesecurity/trufflehog` or `gitleaks` report findings on the repo

**Phase to address:**
Secret hygiene / gitignore completeness phase.

### Pitfall 3: macOS Version Updates Breaking yabai and skhd

**What goes wrong:**
yabai relies on a scripting addition injected into `Dock.app` to manage windows and spaces. Each macOS major and minor release has historically required re-disabling SIP (System Integrity Protection), updating the scripting addition hash in the sudoers config, or waiting for a yabai release that supports the new OS. Updating macOS without checking compatibility first leaves the window manager broken for days until a fix is released or a workaround is documented.

**Why it happens:**
Apple changes internal window server APIs without notice. yabai's scripting-addition injection pattern is inherently fragile against OS changes. The dotfiles repo pins a yabai version indirectly (via Homebrew), but Homebrew auto-upgrades during `brew update` unless pinned explicitly.

**How to avoid:**
Pin yabai to a known-good version in `Brewfile` or with `brew pin yabai`. Before any macOS update, check the yabai GitHub issues for the target OS version. Document the current SIP disable procedure and scripting-addition sudoers entry as comments in the yabai config or a `yabai/README.md`. Use `brew pin yabai skhd` to prevent unintended upgrades.

**Warning signs:**
- macOS updates available in System Settings while yabai/skhd are unverified for that version
- `yabai --check-sa` returns a non-zero exit code after an OS update
- Spaces or window focus commands stop working after `brew upgrade`

**Phase to address:**
Window management stability / version pinning phase.

### Pitfall 4: Configuration Drift Between the Live Machine and the Repo

**What goes wrong:**
Tweaks made interactively (editing `~/.zshrc` directly, adjusting Neovim options inside Neovim, changing a SketchyBar item on the fly) never get committed. The symlinked file is modified in-place so the change is live but it may not be staged or reviewed. Over weeks the repo drifts from the actual working configuration. On a fresh machine bootstrap the "known-good" config from git is actually stale.

**Why it happens:**
Symlinks make the repo and the live config the same file, which means the friction to commit is entirely up to the developer's discipline. There is no automated signal that uncommitted modifications exist.

**How to avoid:**
Run `git status` in the dotfiles repo as part of a daily or weekly habit (a zsh alias or a tmux status-bar widget). Add a startup hook or shell `precmd` function that checks for uncommitted dotfile changes and emits a brief warning. Keep changes small and commit immediately — the conventional-commits discipline already enforced in this repo helps here.

**Warning signs:**
- `git status` shows modified tracked files that have not been staged for days
- A fresh bootstrap produces a noticeably different feel from the daily-driver machine
- `.zshrc` has lines that don't exist in the repo copy

**Phase to address:**
Ongoing maintenance / commit discipline phase; can be automated in the shell environment phase.

### Pitfall 5: Neovim lazy-lock.json Excluded But Plugins Break Silently

**What goes wrong:**
`nvim/lazy-lock.json` is in the root `.gitignore`. Without a committed lockfile, `lazy.nvim` installs the latest commit of every plugin on each new machine bootstrap. If an upstream plugin releases a breaking change between the daily-driver machine and a fresh setup, the new machine has a broken Neovim config that differs from the working one. Debugging this is slow because the symptom (a cryptic Lua error) does not point to the root cause (plugin version mismatch).

**Why it happens:**
Lockfiles are large, noisy diffs, and developers exclude them to keep git history clean. The downside — non-reproducible installs — only manifests when bootstrapping a new machine, which is infrequent.

**How to avoid:**
Track `nvim/lazy-lock.json` in the repo (remove it from `.gitignore`) and commit it whenever intentionally running `:Lazy update`. This is low-noise because the lockfile only changes when you explicitly upgrade plugins. Alternatively, pin each plugin to a specific `commit` or `tag` inside the plugin spec so `lazy.nvim` installs a deterministic version even without the lockfile.

**Warning signs:**
- A fresh Neovim setup on a new machine shows Lua errors not seen on the daily-driver
- `:Lazy` shows plugin versions different from the daily-driver machine
- `lazy-lock.json` is listed as ignored in `.gitignore` (current state)

**Phase to address:**
Neovim plugin determinism phase.

### Pitfall 6: Setup Script Assumes a Single Fixed Username

**What goes wrong:**
`initial-setup-macos.sh` calls `ensure_expected_user` which hard-fails if the current user is not `aslaii`. This makes the script unusable by anyone else (including the same developer if they ever rename the macOS account). Cross-platform support (a stated active requirement in `PROJECT.md`) becomes impossible to test or verify because the guard blocks all other users.

**Why it happens:**
The guard was added as a safety check to prevent accidental runs on shared machines. It solves the right problem (wrong machine) with too blunt an instrument (wrong username = die).

**How to avoid:**
Replace the hard user check with a confirmation prompt when the username does not match an expected value, or remove it entirely and rely on the dotfiles directory check (`ensure_dotfiles_dir`) as the real guard. Machine-specific configuration (MCP server paths, tool install locations) should be driven by `$HOME` and `$(whoami)` at runtime.

**Warning signs:**
- The function `ensure_expected_user` exists in `initial-setup-macos.sh` with a hardcoded string
- `grep -n "aslaii" initial-setup-macos.sh` returns results outside of comments

**Phase to address:**
Bootstrap script portability phase.

### Pitfall 7: Zinit Plugin Order Causing Completion or Syntax Highlighting Failures

**What goes wrong:**
Zinit's Turbo mode defers plugin loading, which means `zsh-syntax-highlighting` or `zsh-autosuggestions` can load before or after `compinit` in non-obvious ways depending on the `wait` parameter. The symptom is either broken tab completion or syntax highlighting that works on login but not in a new tmux pane, or a 400ms+ startup regression caused by double `compinit` calls.

**Why it happens:**
Zinit's deferred loading is powerful but requires explicit ordering of completion-related plugins. Adding a new plugin without understanding the `wait`/`lucid`/`atinit` directive interactions silently introduces ordering bugs.

**How to avoid:**
Load `zsh-syntax-highlighting` and `zsh-completions` last, after `compinit`. Use `zinit cdreplay -q` after all plugin declarations to replay deferred `compdef` calls in a single pass. Profile startup time with `zsh -i -c exit` timing or `zpmod source-study` before and after adding new plugins.

**Warning signs:**
- Shell startup time exceeds 200ms (`time zsh -i -c exit`)
- Tab completion works in a fresh terminal but not after `source ~/.zshrc`
- Syntax highlighting is absent in tmux panes but present in a direct Ghostty session

**Phase to address:**
Shell environment / Zsh configuration phase.

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| Hardcode `/Users/aslaii` in JSON configs | No template logic needed | Repo cannot be used by any other user or account | Never — use `$HOME` |
| Exclude `lazy-lock.json` from git | Cleaner diffs | Non-reproducible Neovim installs on new machines | Only if all plugins are pinned by commit in the spec |
| Single monolithic `.zshrc` | Easy to find everything | Slow startup, hard to isolate breakage, can't disable sections | Never grow past ~150 lines without splitting |
| No `.gitignore` per AI tool subdirectory | Less config to maintain | Any new tool that generates tokens writes them to a tracked-able path | Never — each AI tool dir needs its own `.gitignore` |
| `brew upgrade` without pinning | Always latest features | yabai/skhd break on OS-incompatible versions | Only for tools with stable APIs across macOS major versions |
| `setups/` scripts duplicating symlink logic | Standalone per-client setup | Logic diverges from `initial-setup-macos.sh`, breakage goes undetected | Only at MVP; must be refactored to shared `functions.sh` before second client setup |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| yabai scripting addition | Assuming it persists across macOS updates | Re-run `yabai --install-sa` and update sudoers entry after every OS update |
| Homebrew on Apple Silicon | PATH not updated in scripts that run before `brew shellenv` | Always call `eval "$(brew shellenv)"` before using any brew-installed binary |
| nvm in Zsh | Sourcing nvm eagerly slows shell startup by 200-400ms | Use lazy loading: only init nvm when `node` or `npm` is first invoked |
| MCP servers in Claude Code | Absolute paths in `mcpServers` break when `$HOME` changes | Generate the MCP config section in setup script using `$HOME` substitution |
| Gemini CLI oauth tokens | Tracked by mistake if `gemini/` has no local `.gitignore` | Add `gemini/.gitignore` (currently missing — relies on root `.gitignore` only) |
| tmux TPM plugins | TPM bootstrapped via `git clone` in setup but plugins not installed until `<prefix>I` | Document that manual `<prefix>I` is required after first bootstrap, or automate via `tmux new-session -d` + `tpm` run in setup script |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| Eager nvm init in `.zshrc` | `time zsh -i -c exit` > 500ms | Lazy-load nvm: only source when `nvm`, `node`, `npm`, `npx` first called | Present on any machine with nvm installed |
| Double `compinit` from Zinit plugin order | Completion regeneration on every shell start | Call `compinit` once, use `zinit cdreplay` for deferred plugins | Every new shell start |
| `brew list --formula` per package in install loop | `install_formulae` takes 30+ seconds on rerun | Batch with `brew list --formula` once, diff against desired list | Every rerun of `initial-setup-macos.sh` |
| SketchyBar with many event-driven items | CPU spike on desktop switch, battery drain | Profile with `sketchybar --query bar` and reduce update frequency on non-critical items | Noticeable on battery with 10+ dynamic items |
| Neovim LSP servers downloaded on every new machine | First Neovim startup takes minutes | Track `mason-lock.json` or pre-seed Mason registry cache | Every fresh machine bootstrap |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| AI tool config files without per-directory `.gitignore` | OAuth tokens, session state, or API keys committed | Add a `.gitignore` to every AI tool config directory (`gemini/` currently missing one) |
| MCP server config with hardcoded credentials | Credentials in git history permanently | Store credentials outside the repo; reference via env var or system keychain |
| `claude/settings.json` hook paths with absolute `/Users/aslaii` | Path leaks username; hooks fail on any other machine | Replace with `$HOME`-relative paths or generate at bootstrap time |
| `setups/*.sh` files with client-specific credentials or tokens | Client secrets in a personal public repo | Ensure `setups/` scripts use `op` (1Password CLI) or env vars, never literals |
| Pre-commit hooks not scanning for secrets | Secrets committed before human review | Add `gitleaks` or `trufflehog` as a pre-commit hook |

## "Looks Done But Isn't" Checklist

- [ ] **Symlinks:** `ls -la ~/.claude ~/.config/yabai ~/.config/skhd ~/.config/opencode ~/.config/codex` all point into the repo — verify after every new tool added.
- [ ] **AI tool gitignores:** Every subdirectory housing an AI tool (`claude/`, `gemini/`, `opencode/`, `codex/`) has a `.gitignore` that excludes auth state — `gemini/` currently relies on root `.gitignore` only.
- [ ] **Hardcoded paths:** `grep -rn '/Users/' $(git ls-files)` returns zero results in tracked files (currently fails — `claude/settings.json` and `initial-setup-macos.sh` contain `/Users/aslaii`).
- [ ] **Neovim lockfile:** Either `nvim/lazy-lock.json` is tracked, or all plugins in `nvim/lua/plugins/` specify a `commit` or `tag` pin.
- [ ] **yabai compatibility:** Current macOS version is listed as supported in yabai release notes before running `brew upgrade yabai`.
- [ ] **Idempotency:** `initial-setup-macos.sh` can be run twice on the same machine without error or duplicate state — test with `bash -n` and a dry run after every substantive change.
- [ ] **setups/ coverage:** Every script in `setups/` calls `link_file` from `functions.sh` (or the equivalent) rather than duplicating symlink logic.
- [ ] **tmux plugins:** After a fresh bootstrap, `<prefix>I` is either documented in a README or automated in the setup script.

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| Secret committed to git | HIGH | `git filter-repo --path <file> --invert-paths`, force-push, rotate all exposed credentials immediately |
| yabai broken after macOS update | MEDIUM | `brew uninstall yabai`, install pinned version matching OS, re-run `yabai --install-sa`, update sudoers |
| Neovim config broken by upstream plugin | LOW | `nvim --headless "+Lazy restore" +qa` if lockfile exists; otherwise `:Lazy pin <plugin>` to freeze at last good commit |
| Zinit completions broken | LOW | Delete `~/.zcompdump*`, run `compinit -d`, restart shell |
| Configuration drift discovered on fresh machine | MEDIUM | `diff <(ssh daily-driver "cat ~/.zshrc") ~/.zshrc` to find additions; manually cherry-pick back into repo |
| Broken symlink after tool removal | LOW | `find ~ -maxdepth 3 -type l ! -e 2>/dev/null` to surface all dangling symlinks; remove stale entries |
